# CONTEXT — Heat Map · BR (проектная память для новой сессии)

Прочитав этот файл, ассистент должен понимать архитектуру, модель данных,
решения и подводные камни без повторного расследования. Обновлять при
существенных изменениях. Актуально на: версия кэша **20260924e**.

---

## 1. Что это

Веб-приложение — интерактивная **тепловая карта торговых точек**. Пользователь
грузит слои данными (CSV/XLSX), видит heat map, получает **рекомендации** по
открытию новых точек BR, работает с **адресной программой** (фильтры по
расстоянию/объёму/исключениям) и смотрит **сводку по городу**. Интерфейс на
русском.

- **Карты (независимые):** `comdep`, `other` — Узбекистан; `kg` — **Кыргызстан**.
- Стек: **Leaflet** + растровые тайлы **2ГИС** (см. `CLAUDE.md`), тепло — `leaflet.heat`, парсинг файлов —
  PapaParse + XLSX (SheetJS, грузятся лениво). Всё **без сборки** — статические файлы.
- Хостинг: **фронт — GitHub Pages**, **сервер данных — Render** (Node/Express).

## 3. Git / деплой

- **Пуш — в `main`.** Но параллельно часть работы шла через **PR из ветки
  `claude/design-aesthetic-msaxk3`** → бывают конфликты. **Всегда
  `git pull --rebase origin main` перед пушем.**
- Фронт — **GitHub Pages** из `main` (авто `pages-build-deployment`, «Deploy from
  a branch»; в репо workflow нет). Ошибка `deploy-pages: Deployment failed, try
  again later` обычно транзиентная — контент часто всё равно публикуется;
  помогает «Re-run failed jobs» или пустой коммит.
- **Кэш-бастинг:** `index.html` ссылается на `style.css?v=YYYYMMDD<буква>` и
  грузит `app.js?v=...`. **При любой правке app.js/style.css/boot — поднимать
  версию соответствующего ресурса** (текущий `app.js`: `20260924e`). `index.html` отдаётся
  `no-cache`, но пользователю всё равно советуем hard refresh (Ctrl+Shift+R).
- Коммиты заканчивать трейлером `Co-Authored-By: Claude …` (конкретную версию
  модели подставляет окружение; технический ID модели в артефакты не писать).
- `node --check app.js` перед коммитом; проверять балансы скобок/тегов.
  То же проверяет CI (`ci.yml`) — вместе с ESLint и версией кэша.

## 4. Сервер и данные

- Прод-сервер: `https://hm-server-xpg0.onrender.com` (`window._HM_SERVER_URL` в
  index.html). Тариф Render — **платный** (не засыпает).
- `GET /data` — базовый датасет (ключ `dataset`), только для действующей серверной сессии.
- `POST /data` — заменить базу: роль `admin` + `X-API-Key` (см. §10б — ключ
  выдаётся сессии автоматически).
- `GET/POST /state?map=comdep|other|kg` — общее состояние карты. GET требует
  сессию и доступ к карте, POST — роль `admin` и `X-API-Key`.
- `GET /state/revision?map=…` — дешёвая ревизия для опроса открытыми вкладками (§12в).
- `POST /photo?map=…` / `GET /photo/:id` — фото точек ручного ввода (§10а).
- `GET /health` — health-check.
- `MAPS = ['comdep','other','kg']` в server.js. `storeKey()` в localStorage =
  `hm_state_<currentMap>`.
- **Структура `DATA` (из `/data`):** `cities`, `cig`, `sticks`,
  `districts` (районы Ташкента с `tier` дохода), `field` (грид дохода Ташкента).
  База **UZ-специфична и общая для всех карт** (см. §5). `combined` не хранится.
  Поле `own` — **легаси**: наши точки переехали в слои состояния (см. §10), в
  базу пишется пустой массив, чтобы старые вкладки с закэшированным
  `index.html` (там была проверка `!d.own`) продолжали грузиться. Новый
  boot-скрипт проверяет только флаг `empty`.

## 5. Карты и страны (UZ / KG)

- **Пер-страновой конфиг** `COUNTRIES` (app.js): у каждой страны свой список
  городов (плашка сверху), центроиды (`cityOf`), справочник вкладки «Город»
  (`UZ_STATS`/`KG_STATS`), доля курящих, валюта зарплаты (`wageUnit/wageCur`).
- `MAP_COUNTRY` привязывает карту к стране; **`applyCountry(currentMap)`
  вызывается первым в `startApp`** и заполняет
  `CITIES/CC/CITY_STATS/SMOKE_*/WAGE_*`.
- **KG-данные (2025):** население — Нацстатком КР (stat.gov.kg); зарплаты по
  регионам за 2025 (тыс. сом/мес); курение — ВОЗ 2024 (муж. 32,8%, жен. 2,9%).
  Города: Бишкек, Ош, Джалал-Абад, Каракол, Токмок, Узген, Нарын, Талас, Баткен.
- **Ограничение KG:** база (cig/sticks/districts) — UZ и общая, но она больше не
  рисуется на карте. Наши точки у каждой карты свои (лежат в её состоянии),
  поэтому KG-карта чистая: пока в неё не загрузили точки, метрика «на 1 нашу
  точку» = «—», расстояния = «—», адресная программа сообщает, что нет
  ориентиров. «Районы» скрыты вне UZ; KG-карта центрируется на Бишкеке.

## 6. Модель слоёв

- **Главная вкладка «Карта» показывает только загруженные пользователем слои**
  (`heatKeys` = ключи `custom_*`). Стартует пустой со заглушкой.
- `cig`/`sticks` остаются в `DS`, но **не в `heatKeys`** — не рисуются/не в списке
  (данные для служебных нужд).
- **Загрузка:** «Загрузить слой (файл)» → CSV/XLSX → модалка (имя + цвет) → слой
  из файла (`enrich(toRecs(rows))`) → в `heatKeys`, карта подлетает к данным.
- **Карточка слоя:** вкл/выкл, палитра, цвет, интенсивность, прозрачность,
  ✎ переименовать, ⬆ Обновить данные, × удалить (с `confirm`).
- Колонки файла: `name, lat, lon, value` (+опц. `addr, code, hours`). `value` →
  `vol` (яркость тепла). Нет `value` → `vol=1`.
- Ключевые функции: `buildHeatUI`, `renderHeat`, `confirmLayerModal`/
  `openLayerModal`/`parseSheet`/`focusNewLayer`, `toRecs`/`enrich`.
- **Парсинг файлов ленивый** (`ensureSheetLibs`); все загрузки через `parseSheet`
  (try/catch + тост «Обработка файла…»).

## 7. Рекомендации и Адресная программа (вкладка «Анализ»)

Обе работают **по загруженным слоям** (не по cig/sticks).
- **Рекомендации:** `#rec-basis-sel` — выбор слоя-основы (`recBasis`).
  `renderRecs()`: `DS[recBasis].recs`, фильтр по городу и `s.nd > covR`
  (расстояние до ближайшей нашей точки, см. §10), жадное подавление, топ-N.
- **Адресная:** источник (`addrSrcKey`) = heat-слой или слой точек (`__cpt__`).
  `__shipment__` и `__own__` удалены. Референс — любой слой наших точек
  (`__cpt__<id>`), с точками. `runAddrFilter`/`previewAddrOnMap`/`exportRetraffic`.
- Селекторы перестраиваются при изменении слоёв (`buildRecBasisSel`+
  `buildAddrSrcSel`+**`buildRtExclUI`**). `focusNewLayer` долго не вызывал
  последний — новый слой не появлялся в исключениях до перезагрузки.
- **Ленивая загрузка ломала адресную молча (сентябрь 2026).** Записи тепловых
  слоёв грузятся только для видимых слоёв и основы рекомендаций, поэтому:
  - список исключений считал точки по `recs.length` и прятал незагруженные
    слои → теперь `layerRecordCount()` берёт число из манифеста (`stats.n`);
  - отмеченный, но незагруженный слой-исключение не исключал ничего, а слой-
    источник давал ноль точек — **без всякого признака ошибки**. Теперь
    `previewAddrOnMap`/`exportRetraffic` сначала ждут `ensureAddrLayers()`.
- **Шаг 4 (исключения) объясняет себя** (`syncExclHint`): живой текст под
  ползунком пишет, что произойдёт с текущими настройками. Подпись «ближе чем»
  переключается на «дальше чем» для операторов `>`/`≥` (они переворачивают
  правило) и подсвечивается предупреждением. В подсказке ⓘ — правило про
  совпадение колонки `code`: оно исключает адрес независимо от расстояния.
- **Превью адресной программы в легенде** (`addrPreview`): оранжевые кандидаты
  и синие ориентиры со счётчиками. Кнопка «На карте» — переключатель
  («Убрать с карты»), всё очищение идёт через `clearAddrPreview()`, чтобы
  легенда и подпись кнопки не разошлись с тем, что на карте.

## 8. Города и `cityOf`

- `cityOf(lat,lon)` → ближайший центроид из `CC` (заполняется `applyCountry`:
  из `DATA.cig.recs` где есть, иначе хардкод-центры страны).
### 8а. Охват Ташкента: город или город + область (сентябрь 2026)

Правило «ближайший центр в пределах 60 км» относит к Ташкенту всю область
(Чирчик, Ангрен). В фильтре городов появился переключатель **«Город + область»**
(по умолчанию, прежнее поведение) и **«Только город»** — виден на UZ-картах при
выбранном Ташкенте. `tashkentScope` сохраняется в состоянии.

- «Только город» = **настоящие границы**: объединение полигонов районов из
  `DATA.districts` (те же, что рисует кнопка «Районы»), а не радиус.
  `tashkentRings()` + `pointInRing()` (ray casting), отсечение по bbox.
- **`recInSelection(r)` — единственная проверка принадлежности.** Раньше пути
  было два: тепловые записи сравнивались по строке `fil`, слои точек —
  геометрически (`pointInCity`). Режим, доходящий только до одного из них, был
  бы хуже его отсутствия. `cityMatches()` удалена как мёртвая.
- Результат мемоизируется по округлённым координатам (`_tshkCache`): в слое
  десятки тысяч точек, а фильтр пересчитывается на каждый рендер. Сами записи
  не засоряются служебными полями.
- Пустой результат `tashkentRings()` **не кэшируется** — районы приходят с
  `/data` позже; без границ режим падает на обычное правило, а не обнуляет карту.

- При загрузке состояния `fil` каждой точки **пересчитывается** (cityOf) — чинит
  старые слои. Выбор города сверху фильтрует тепло/рекомендации/адресную;
  `fitView()` летит к данным города.

## 9. Интенсивность тепла

`renderHeat()`: каждый слой нормируется **по своему p90** (магнитуда `value` не
важна), gamma-подъём `t^0.55` + порог `0.18` (слабые точки видны). Ползунок
«Интенс.» (`d.intensity`) — множитель. Глобальная «Общая яркость» (`heatBoost`)
через прозрачность canvas (`applyHeatCanvas`/`restyleHeatCanvases`).

### 9а. Палитры и наборы цветов (сентябрь 2026)

- `HEAT_RAMPS` — 12 палитр + `custom`: warm, cool, viridis, **cividis**
  (безопасна при дальтонизме), inferno, magma, **plasma**, turbo, **teal**
  (фирменная), **forest**, **rose**, **mono**. Имена — `RAMP_NAMES`.
- Выбор — **сетка чипов с настоящим градиентом** (`.ramp-chip`), а не `<select>`:
  набор выбирается по виду. `rampCss(grad, from)` строит CSS-градиент и
  переиспользуется в чипах, превью и легенде.
- `SWATCHES` — 14 разнесённых по тону цветов; общий ряд свотчей (`.sw-row`) для
  «своего цвета» тепловых слоёв **и** для маркеров слоёв точек.
- `layerKeyColor(d)` — цвет-представитель палитры (стоп 0.78) для точки в
  заголовке карточки и для ярлыков; раньше точка показывала `d.color`, который
  при выбранной палитре ни на что не влиял.
- Цвет слоя точек: на `input` перерисовываются только маркеры, зависимые списки
  обновляются на `change` — иначе карточка пересобиралась на каждое движение
  пипетки и выбор обрывался.

### 9б. «Ярлыки» — тачпоинты теплового слоя

Кнопка `🏷 Ярлыки` в карточке слоя (`d.showTags`, сохраняется в состоянии).

- Рисует **точки самого слоя** поверх тепла; клик → карточка из загруженного
  файла: имя, адрес, часы, код, город, значение + имя слоя.
- Ограничения по производительности: только видимая часть карты
  (`map.getBounds().pad(.08)`), canvas-рендерер в пане `tags` (zIndex 470, под
  маркерами точек), потолок `TAG_LIMIT = 1200` — при переполнении остаются
  точки с наибольшим `vol`, а `#tag-note` пишет «показано N из M».
- `renderTags(force)` сверяет сигнатуру (ключи+цвета+города+границы), иначе
  `renderHeat()` пересобирал бы до 1200 маркеров на каждый кадр ползунка.
- Тултипы вешаются только если точек ≤ 300.
- Легенда: тепловой слой показывается **полосой-градиентом** + счётчиком, слой
  с включёнными ярлыками помечен 🏷.

## 10. Наши точки (вкладка «Точки»)

`customPtLayers` — слои маркеров (не тепло): видимость, цвет, форма, размер,
прозрачность и радиус охвата, рендер в `cptRoot` (полностью чистится каждый
рендер — защита от осиротевших групп).

**Это и есть «наши точки».** Закреплённого раздела «Наши точки · IQOS» с двумя
зашитыми слоями (BR / 2nd SE) и датасета `own` больше нет — удалены 07.2026 по
решению владельца: всё, что загружено во вкладке «Точки», считается нашей сетью.

- Вкладка «Точки» использует тот же accordion/card pattern, что и тепловые слои:
  скрытие/показ через единый switch, раскрываемые настройки, переименование,
  «Соло», обновление данных и удаление. Видимость слоя на карте на расчёты
  `ourPts()` **не влияет**: скрытый слой всё равно наш.
- `ourPts()` — плоский список точек **всех** слоёв вкладки.
- `ourPtsInCity(city)` — сколько наших точек в городе. У слоёв точек нет колонки
  города, поэтому берётся ближайший центр и только в пределах 60 км.
- `enrichNd(recs, ix)` — считает `nd` (расстояние до ближайшей нашей точки).
  Вынесено из `enrich()`, потому что при изменении наших точек надо пересчитать
  только `nd`, а тяжёлый локальный спрос `ld/lc` — не надо.
- `reenrichAll()` — вызывать **при любом изменении состава наших точек**
  (загрузка файла в слой, удаление слоя): пересчитывает `nd` во всех тепловых
  слоях и перерисовывает рекомендации. Без этого рекомендации остаются
  посчитанными по старому набору точек.
- **Порядок в `applySnapshot` критичен:** `customPtLayers` восстанавливаются
  **до** тепловых слоёв — иначе `enrich()` посчитает покрытие по ещё не
  заменённому набору точек.
- Слой точек может служить референсом/исключением в адресной программе.

### 10а. Ручной ввод точек (сентябрь 2026)

Точки можно заводить **по одной через форму**, а не только файлом. Они попадают
в **обычный слой точек** с флагом `manual: true` — поэтому у него те же
инструменты, что у загруженных слоёв (цвет, иконка, размер, прозрачность,
радиус охвата, «Соло», переименование), и он стоит в одном списке с ними.

- Отличия ручного слоя в карточке: вместо «⬆ Данные» — **«+ Точка»**, и внутри
  список точек (клик — перелёт к точке, ✎ — правка). Правка только у админа.
- Точка-карточка: `{id, name, dms, equip, sales, comment, color, lat, lon, photos[]}`
  в `l.recs`. **`color` — цвет конкретной точки**; пусто = наследуется от слоя
  (тогда перекраска слоя доходит до точки). Свой цвет действует и на маркер, и
  на круг охвата, и на плашку в попапе, и на точку в списке слоя. Иконки
  кэшируются по цвету (`iconFor`) — иначе SVG рисовался бы на каждую точку. Попап с карточкой рисуется для любой точки, у которой есть эти
  поля (`isManualRec`), в цвете своего слоя.
- Форма (`openRetailForm(layerId, recId)`) выбирает **слой назначения** или
  заводит новый (`createManualLayer`). Смена слоя у существующей точки
  переносит её между слоями.
- Координаты — вручную или кнопкой «Указать на карте» (`startGeoPick`;
  обработчик снимается адресно, `map.off('click', handler)`).
- Ручные точки входят в `ourPts()` → после любой правки `reenrichAll()`.
- **Выгрузка в Excel** (`exportManualPts(layerId)`): ссылка «⬇ Excel» в карточке
  ручного слоя, плюс «Все ручные точки в Excel» под вкладкой (показывается,
  только когда заполненных ручных слоёв больше одного). Колонки: слой, название,
  ДМС-код, оборудование, продажи, широта, долгота, город, цвет, комментарий, число
  фото и **прямые ссылки** на них (вставить картинку в XLSX нельзя; ссылка
  открывается в браузере, где уже есть сессия). Продажи и координаты остаются
  числами — иначе Excel не сортирует и не суммирует; `0` продаж не схлопывается
  в пустую ячейку.
- **`stateFingerprint` дигестит поля ручных точек.** Правка карточки не меняет
  их количество, и без этого сохранение на сервер пропускалось как «состояние не
  изменилось».
- **Миграция:** старый отдельный список `retailPts` переносится при загрузке в
  слой «Торговые точки» (`cpt_retail_legacy`), с проверкой по `id` точки —
  состояние, где есть и старое поле, и уже мигрированный слой, не задваивается.

**Фото (важно).** В состоянии их нет — только `id`. Состояние и так весит
мегабайты и уходит целиком на каждое сохранение; три фото с телефона сделали бы
его неотправляемым.

- Клиент сжимает: длинная сторона ≤ 1400 px, JPEG q0.82 (`compressImage`).
- `POST /photo?map=…` (владелец) — data URL; сервер режет не-картинки и >4 МБ,
  `id = sha256(map|bytes).slice(0,32)` → повторная загрузка того же файла
  **не создаёт дубликат**. Таблица `photos(id, map, mime, bytes, created_at)`,
  локальный фолбэк — `server/photos/` (в .gitignore).
- `GET /photo/:id` — только сессии с доступом к этой карте (иначе 403),
  `Cache-Control: private, max-age=1y, immutable`.
- Клиент грузит через `authFetch` в blob-URL (`_photoUrls`), **не через
  `<img src>`**: у картинки нет заголовка авторизации, а сессия может жить в
  памяти вкладки (фронт на Pages — другой домен).
- Полноэкранный просмотр — `#photo-lightbox` (стрелки, ←/→, Esc).
- Известный долг: удалённые фото остаются в БД (GC не делали — из-за
  дедупликации один `id` может использоваться несколькими точками).

### 10б. Ключ записи и ошибки 401

**Ключ записи выдаёт сервер (сентябрь 2026) — вручную вводить не нужно.**
`/auth/login` и `/auth/me` возвращают `writeKey` для роли `admin`:
`HMAC(SESSION_SECRET, 'write|' + session token)`. Клиент кладёт его в
`SERVER_KEY` (`applyWriteKey`) при входе и при восстановлении сессии после F5.
`verifyKey` принимает **либо** его, **либо** статический `API_KEY` из окружения
(для скриптов). Ключ нельзя вычислить без `SESSION_SECRET` и он не подходит к
другой сессии — поэтому заголовок по-прежнему работает как защита от CSRF
(чужая страница не подставит его, даже если браузер пошлёт cookie). Ручное поле
в «Данные → Доступ к записи» осталось запасным путём (старый сервер).

`SERVER_KEY` по-прежнему живёт **только в памяти вкладки**
(`localStorage['hm_admin_key']` активно удаляется), но теперь это незаметно.
У сервера **два разных 401**: «Invalid or missing X-API-Key header»
(нет ключа записи) и «Authentication required» (нет сессии).

- `serverErrorText(res)` разворачивает ответ в понятную причину — раньше
  показывался голый «HTTP 401», и причина была не видна.
- Форма точки показывает **постоянную плашку с полем ключа** (`#rp-key-warn`),
  пока ключа нет; кнопка «Добавить фото» заблокирована.
- `pushToServer` без ключа раньше **молча выходил** — правки владельца никуда
  не уходили без единого признака. Теперь ставит бейдж «Нет ключа записи».

## 12. Состояние и синхронизация

- Автосейв (debounce **1500 мс**) → `doSave` → localStorage + `pushToServer`.
  `buildStateSnapshot()`/`applySnapshot()`.
- **Slim-recs (важно):** в состоянии хранятся **только входные поля точек**
  (`lat/lon/vol` + `name/addr/code/hours`, координаты округлены), а `nd/ld/lc/fil`
  и `stats` **пересчитываются при загрузке** (`slimRecs` на сохранении, `cityOf`+
  `enrich`+`statsOf` на загрузке). Причина: состояние разрослось до ~7 МБ и POST
  перестал проходить («Сервер недоступен» при живом сервере) — slim ужимает ~вдвое.
- **Анти-клоббер при гидрации:** `startApp` выбирает local/server по таймстампу,
  но **не даёт пустому источнику затереть слои** непустого (`hasLayers`). Если у
  пользователя «пропали» слои — они на сервере; помогает hard refresh или
  `localStorage.clear()` в консоли.
- Кэш датасета: boot-скрипт кэширует `/data` в `localStorage['hm_dataset_cache_v1']`
  (stale-while-revalidate). localStorage близко к лимиту (~5 МБ) — записи в
  try/catch, при переполнении просто не кэшируется.

### 12в. Публикация обновлений владельцем (сентябрь 2026)

Раньше остальные узнавали о новой версии только перезагрузкой страницы.

- **`GET /state/revision?map=…`** → `{revision}` = `state._savedAt`. Отвечает из
  30-секундного `stateReadCache`, поэтому опрос дешевле `/state/meta` (тот
  пересобирает манифест слоёв на каждый запрос). **Контракт (проверен):**
  `revision` побайтно равен `_savedAt` манифеста и тому, что `pushToServer`
  кладёт в `_activeStateRevision` — иначе баннер зациклится.
- **Слежение:** `startUpdateWatcher()` в конце `startApp` — опрос каждые 45 с +
  на `visibilitychange` (возврат во вкладку) + на `online`. Если ревизия ≠
  `_activeStateRevision` → баннер `#update-banner` над картой. Владелец своего
  же сохранения не видит (`pushToServer` двигает `_activeStateRevision`).
- **Применение (`runUpdate`)**: манифест → `applySnapshot` → `ensureLayerRecords`
  (только видимые слои + основа рекомендаций). Прогресс **настоящий**:
  `_loadProgressHook` считает загруженные записи против суммы `stats.n` из
  манифеста; карта обесцвечена и возвращает цвет через `--upd-gray` (1→0) на
  `body.updating #map`. Успех → время версии + бейдж; сбой → `updateFailureCopy`
  (401 / 403 / таймаут / офлайн) с конкретными шагами и «Повторить».
- При сбое `_activeStateRevision` **откатывается**, чтобы повтор начался с
  чистой ревизии, а баннер вернулся.
- `applySnapshot` в ветке `st._meta` чистит `_heatCache/_fullPtsCache/_heatMaxCache`
  — иначе на новых записях могло отрисоваться тепло прошлой ревизии.
- Настройки вида у зрителя при обновлении заменяются версией владельца — это
  осознанно: у всех одна картина.

## 12а. Пространственный индекс (поиск ближайшей точки)

`buildPtIndex(pts)` + `nearestPt(ix, lat, lon)` — грид 0.05° (≈5,5 км) с обходом
по кольцам. Используются в `enrichNd()` (расстояние `nd` до ближайшей нашей
точки) и в `runAddrFilter()` (ближайший референс). Результат **идентичен брутфорсу**:
обход прекращается только когда найденное расстояние заведомо меньше всего, что
может лежать за кольцом; если оценка не сомкнулась за 60 колец — честный перебор.
Измерено в браузере (20 000 запросов): 1,6× быстрее при 30 опорных точках и
4,5× при 5 000. **Не менять размер ячейки или условие выхода без сравнения с
брутфорсом на случайных данных.**

## 13. Безопасность

- **Ключ на сервере проверяется до разбора тела запроса** (middleware в
  `server.js`): иначе аноним мог заставить сервер принять и распаковать 50 МБ
  JSON и только потом получить 401. Плюс `X-Content-Type-Options`,
  `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, снят `x-powered-by`.
- **`render.yaml` больше не содержит значение `API_KEY`** (`sync: false`).
  Старое значение из истории репозитория считать утёкшим — **владельцу нужно
  задать новый ключ в дашборде Render и ввести его в браузере.**
- **Запись на сервер — только у владельца.** Сначала нужна серверная HttpOnly-сессия
  с ролью `admin`, затем ключ **не из бандла** вводится в «Данные → Доступ к записи»
  и хранится только в памяти текущей страницы. `pushToServer`/`pushDataset` требуют
  `isAdmin() && SERVER_KEY`; `server.js` дополнительно проверяет `X-API-Key == API_KEY`.
  `AUTH_USERS_JSON`, `SESSION_SECRET` и `API_KEY` задаются только в окружении Render.
- **P1 auth hardening:** `/auth/login` ограничивает пять неудачных попыток за 15 минут
  по двум bounded buckets — normalized IP+username и normalized username — чтобы managed
  proxy IP rotation не обходил лимит; неизвестные пользователи проходят через
  startup-generated dummy scrypt verification. Bearer fallback и admin API key не
  записываются в `sessionStorage`/`localStorage`; старые credential keys удаляются при старте.
- **XSS:** пользовательские значения экранируются `esc()` перед вставкой в
  innerHTML/попапы/тултипы/`<option>`.
- **Файлы не в git:** данные живут на сервере + в браузере; `.gitignore` исключает
  server/state\*.json, .env, dataset-дампы.
- Глобальный обработчик ошибок (`error`/`unhandledrejection` → лог + тост).
  Полноценный Sentry — когда будет DSN.
